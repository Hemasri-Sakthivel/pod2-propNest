1. Executive Summary

The IAM module is the identity backbone of PropNest. It is responsible for:

  • Authentication — verifying who a user is (registration, login, logout, token refresh).
  • Authorization — deciding what a user may do, based on one of six roles (OWNER, TENANT, PROPERTY_MANAGER, TECHNICIAN, FINANCE_EXECUTIVE, REAL_ESTATE_ADMIN).
  • User lifecycle management — admins create users, change their status (Active / Inactive / Suspended), and reassign roles.
  • Self-service — any logged-in user can view and update their own profile and change their password.
  • Auditing — every security-relevant action is written to an immutable audit log for regulatory traceability.

It issues short-lived JWT access tokens (30 minutes) for stateless authentication and long-lived refresh tokens (7 days, stored in the database) so sessions can be renewed and revoked. The module is designed as one slice of a larger modular monolith, sharing a common response/exception foundation with future modules (Property Listing, Tenant Onboarding, Rent & Deposit, Maintenance, Notifications).

3. Project Structure & Layered Architecture

The codebase follows a layered (n-tier) architecture inside a module-per-domain package layout. Each business domain gets its own package tree; within it, responsibilities are separated into layers.

3.1 Folder structure

├── common/                            (cross-cutting, shared by all modules)
│   ├── exception/                     (shared exceptions + global handler)
│   └── response/                      (ApiResponse, ErrorResponse wrappers)
├── config/                            (app-wide beans, e.g. PasswordEncoder)
└── module/
    └── identityAccessManagement/      (the IAM module)

        ├── controller/                (5 REST controllers - the web layer)
        ├── service/                   (business logic + audit helpers)
        ├── repository/                (Spring Data JPA interfaces)
        ├── entity/                    (JPA entities + enums - the data model)
        ├── dto/                        (request/response data carriers)
        ├── security/                   (JWT service, auth filter, context, guard)
        └── exception/                  (module-specific exceptions + handler)

3.2 The layers and why they exist

LayerResponsibilityWhy separated
Controller (web)Translate HTTP requests into method calls; map results to HTTP responses and status codes.Keeps transport concerns (HTTP, JSON, status codes) out of business logic. Controllers stay "thin".
Service (business)Enforce business rules, orchestrate repositories, manage transactions, write audit logs.Single place for rules; reusable by multiple controllers; independently unit-testable with mocks.
Repository (data)Read/write entities to the database via Spring Data JPA.Abstracts persistence; swappable; derived queries remove boilerplate SQL.

DTO (contract)Shape the data crossing the API boundary.Decouples the public API from the internal schema (see §7).

Separation of concerns means each layer has one reason to change. A change in JSON shape touches only DTOs; a new business rule touches only services; a database column rename touches only entities. This makes the system easier to test, reason about, and extend.

4. Application Bootstrap & Configuration

4.1 PropNestApplication.java

@SpringBootApplication
public class PropNestApplication {
    public static void main(String[] args) {
        SpringApplication.run(PropNestApplication.class, args);
    }
}
  • What: the entry point that starts the embedded server and the Spring context.
  • @SpringBootApplication: a meta-annotation combining @Configuration (this class can define beans), @EnableAutoConfiguration (Boot auto-configures the datasource, JPA, web stack from the classpath), and @ComponentScan (discovers all @Component/@Service/@RestController/@Repository beans under com.cog.propNest).
  • How it connects: because the scan root is com.cog.propNest, every class in common, config, and module.* is automatically wired.

4.3 config/SecurityBeansConfig.java

@Configuration
public class SecurityBeansConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
  • What: publishes a single PasswordEncoder bean backed by BCrypt.
  • Why: BCrypt is a deliberately slow, salted, adaptive hash — the industry standard for storing passwords. A shared bean means every service hashes/verifies identically.
  • @Configuration / @Bean: marks a class that contributes beans; the @Bean method's return value becomes a managed singleton injected wherever PasswordEncoder is required.

4.4 module/.../config/RoleSeeder.java

  • What: on startup, inserts the six fixed roles (ids 1–6) if they are not already present.
  • Why: roles are reference data with fixed ids mandated by the API contract (e.g. roleId 6 = REAL_ESTATE_ADMIN). Seeding guarantees they always exist before any user is created.
  • How: it exposes an ApplicationRunner bean; Spring Boot runs it once the context is ready. It checks existsById before saving, making it idempotent across restarts.

5. Data Model (Entities & Enums)

Four tables model the domain. Entities are the single source of truth for the schema; Hibernate generates DDL from them.

5.1 Entity-relationship overview

TableKey columnsRelationships
rolesroleId (PK), roleNameOne role → many users
usersuserId (PK), roleId (FK), name, email (unique), phone, passwordHash, statusMany users → one role
user_sessionsessionId (PK), userId, refreshToken, createdAt, refreshTokenExpiryTime, statusReferences a user (by id)

5.2 Role.java

Maps the roles table. @Id on roleId with no generator because ids are fixed reference values. Lombok @Getter/@Setter/@NoArgsConstructor/@AllArgsConstructor generate the accessors and constructors.

5.3 User.java

@Entity @Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = IDENTITY) private Long userId;
    @ManyToOne(fetch = EAGER, optional = false)
    @JoinColumn(name = "roleId", nullable = false) private Role role;
    @Column(unique = true, length = 150) private String email;
    @Column(name = "passwordHash") private String passwordHash;
    @Enumerated(STRING) private UserStatus status;
}
  • @Entity / @Table: declares a persistent class and the table it maps to.
  • @Id + @GeneratedValue(IDENTITY): primary key, auto-incremented by the database.
  • @ManyToOne + @JoinColumn: the foreign-key relationship to roles; many users share one role. optional=false enforces that every user has a role.
  • @Column(unique=true): enforces the email uniqueness constraint at the database level — a second safety net behind the service-level check.
  • @Enumerated(STRING): stores the status enum as text (A/I/S) rather than a fragile ordinal number.
  • passwordHash: only the BCrypt hash is ever stored — the raw password never persists and is never returned.

5.4 UserSession.java

Maps user_session. Stores the long-lived refresh token, its creation time, its expiry, and a status (ACTIVE/REVOKED). Access tokens are stateless and are not stored; only the refresh token is persisted so it can be rotated and revoked on logout.

5.5 AuditLog.java

Maps audit_log. An append-only record of an action (USER_LOGIN, PASSWORD_CHANGED, …), the entity type, the user id, and a timestamp. There are no update/delete paths — logs are immutable by design.

5.6 Enums: UserStatus & SessionStatus

  • UserStatus — A (Active, can log in), I (Inactive, soft-deleted, record retained for audit), S (Suspended, cannot log in).
  • SessionStatus — ACTIVE (refresh token usable) or REVOKED (after logout/rotation).

6. Repositories (Data Access Layer)

Each repository is an interface extending JpaRepository<Entity, IdType>. Spring Data generates the implementation at runtime, providing CRUD plus any derived query methods (the method name describes the query, so no SQL is written).

RepositoryKey methods & purpose
RoleRepositoryfindByRoleNameIgnoreCase — look up a role by name irrespective of case.
UserRepositoryfindByEmailIgnoreCase, existsByEmailIgnoreCase (login & duplicate checks), findByRole_RoleNameIgnoreCase, findByStatus, and the combined findByRole_RoleNameIgnoreCaseAndStatus (admin list filters).
UserSessionRepositoryfindByRefreshToken — locate a session during refresh/logout.
AuditLogRepositoryfindAllByOrderByTimeStampDesc and findByUserIdOrderByTimeStampDesc — newest-first audit views.

Why JPA/Hibernate: it maps rows to objects automatically, manages the persistence context and dirty-checking (modified entities are flushed without an explicit save), and lets us express most queries as type-safe method names. The nested property syntax Role_RoleName traverses the user.role.roleName association.

7. DTOs (Data Transfer Objects)

All DTOs are Java records — immutable, concise carriers. They define the exact JSON the API accepts and returns.

Why entities are never exposed directly

  • Security: entities carry sensitive fields (e.g. passwordHash). DTOs expose only safe fields, so a hash can never accidentally serialize into a response.
  • Stability: the public contract is decoupled from the database. Renaming a column does not break clients.
  • Validation: request DTOs hold Bean Validation annotations, keeping input rules at the boundary.
  • Performance/clarity: each endpoint returns precisely the fields it needs — no lazy-loading surprises or over-fetching.

8. Services (Business Logic Layer)

Services hold all rules and orchestration. They are annotated @Service (a @Component stereotype) and use @Transactional so a method runs in a single database transaction (rolled back automatically on a runtime exception). Read-only methods use @Transactional(readOnly = true) for efficiency.

8.1 AuthService

  • register — validates the roleId exists (else InvalidRoleException), rejects duplicate emails (EmailAlreadyExistsException), BCrypt-hashes the password, saves the user as Active, and audits USER_REGISTERED.
  • login — loads the user by email, verifies the password with the encoder, rejects non-active accounts (AccountNotActiveException), creates an ACTIVE session with a fresh refresh token, mints an access token, audits USER_LOGIN, and returns both tokens + identity.
  • logout — finds the session by refresh token and sets it REVOKED (idempotent if absent); audits USER_LOGOUT.
  • refreshToken — validates the session is present, ACTIVE, and not expired (else InvalidRefreshTokenException), then issues a new access token and audits TOKEN_REFRESHED.

8.2 UserSelfService

Self-service for the authenticated user: getProfile, updateProfile (name/phone only), and changePassword (verifies current password — else IncorrectPasswordException — then stores a new hash). Each mutating action is audited.

8.3 AdminUserService

Admin operations: createUser, getAllUsers (optional role/status filters; an invalid status string raises InvalidUserStatusException), getUserById (UserNotFoundException if absent), updateStatus, and updateRole. Status parsing is case-insensitive and constrained to the enum.

8.4 RoleService & AuditLogService

  • RoleService.getAllRoles — returns all roles sorted by id (for admin dropdowns).
  • AuditLogService — getAllLogs (system-wide) and getLogsForUser (validates the user exists first).

8.5 AuditService & AuditActions

AuditService.record(userId, action) builds and saves an AuditLog stamped with the current time. AuditActions centralises the action-name constants so spellings never drift. Every other service depends on this one helper, keeping audit writes consistent.

9. Controllers (Web Layer)

Controllers are annotated @RestController (every method returns a value serialized to JSON) and @RequestMapping (a shared URL prefix). They are intentionally thin: read the request, call one service method, wrap the result in a ResponseEntity with the right status. No business rules live here.

Why controllers should be thin

If rules lived in controllers they could not be reused by other entry points (schedulers, messaging, other controllers) and would be hard to unit-test without spinning up the web layer. Thin controllers keep the system testable and the rules in one place.

10. Security & JWT (IAM Core)

10.1 What is a JWT?

A JSON Web Token is a compact, URL-safe, digitally signed token carrying claims about the user. It has three dot-separated, Base64URL-encoded parts:

PartContents
HeaderThe token type (JWT) and signing algorithm (HS256 / HMAC-SHA256).
PayloadThe claims: iss (issuer = propNest-IAM), sub (the userId), custom email and role claims, iat (issued-at), exp (expiry).
SignatureHMACSHA256(base64(header) + "." + base64(payload), secret). Any tampering invalidates it because the secret is known only to the server.

Why stateless: the access token itself carries the identity and is cryptographically verifiable, so the server need not store session state or hit the database to authenticate a request. This scales horizontally — any instance can validate any token.

AdvantagesLimitations / mitigations
No server-side session store; scales across instances; self-contained identity; fast verification.Cannot be revoked before expiry → mitigated with short 30-minute lifetimes and a separately stored, revocable refresh token for renewal/logout.

10.2 JwtService

  • generateAccessToken(user): builds and signs a JWT with subject=userId and email/role claims, expiring in 30 minutes.
  • parseAccessToken(token): verifies the signature and issuer, checks expiry, and returns a CurrentUser(userId, email, role). On expiry/tampering/malformation it throws InvalidTokenException (HTTP 401).
  • generateRefreshToken(): a 48-byte cryptographically random, URL-safe string (opaque, not a JWT) — stored in the DB so it can be revoked.
  • refreshTokenExpiry(): computes the 7-day expiry instant.
  • The signing key is built once from the Base64 secret using Keys.hmacShaKeyFor(...).

10.3 JwtAuthenticationFilter

A OncePerRequestFilter (runs once per request, before controllers) that enforces authentication on protected IAM paths:

  1. If the path is outside /IAM or is a public endpoint (register, login, refresh-token), it passes through untouched.
  2. Otherwise it extracts the Authorization: Bearer <token> header. Missing token → writes a 401 JSON body directly.
  3. It validates the token via JwtService; on success it binds the CurrentUser to AuthContext and continues the chain; on failure it writes 401.
  4. A finally block always clears AuthContext so identity never leaks between requests on a reused thread.

10.4 AuthContext, CurrentUser, AccessGuard, RoleNames

  • CurrentUser — an immutable record (userId, email, role) representing the authenticated caller.
  • AuthContext — a ThreadLocal holder. set/clear are called by the filter; require() returns the caller or throws TokenMissingException (401). It lets controllers/services read the caller without passing it through every method signature.
  • AccessGuard.requireAdmin() — reads the current user and throws AccessDeniedException (403) unless the role is REAL_ESTATE_ADMIN. Admin controllers call it first.
  • RoleNames — string constants for the six roles, preventing typos in comparisons.

10.5 Authentication & authorization flow

Login:    client -> POST /auth/login -> AuthService verifies password
          -> store refresh-token session -> return access + refresh tokens

Protected call:
   client sends "Authorization: Bearer <access>"
   -> JwtAuthenticationFilter validates token -> AuthContext.set(currentUser)
   -> Controller (AccessGuard.requireAdmin() for admin routes)
   -> Service -> Repository -> DB -> DTO response
   -> filter clears AuthContext

Renewal:  access token expires (30 min) -> client calls POST /auth/refresh-token
          with the still-valid refresh token -> new access token issued

Logout:   POST /auth/logout revokes the refresh-token session;
          the client discards the (stateless) access token.

11. Error Handling Strategy

Errors are modelled as typed exceptions and translated centrally, so no controller contains try/catch and every error returns the same JSON shape: { status, message, path, timestamp }.

11.1 Module exceptions (identityAccessManagement/exception)

All extend a common base IamException, which carries the HTTP status each maps to. A single advice (IamExceptionHandler, @RestControllerAdvice, highest precedence) converts any IamException into the standard error body using that status.

ExceptionHTTPRaised when
UserNotFoundException404userId not found
EmailAlreadyExistsException409duplicate email on register/create
InvalidCredentialsException401wrong email/password at login
AccountNotActiveException401suspended/inactive user logs in
InvalidRefreshTokenException401refresh token unknown/expired/revoked
TokenMissingException401no token on a protected endpoint
InvalidTokenException401malformed/expired/bad-signature access token
AccessDeniedException403authenticated but not admin
InvalidRoleException400unknown roleId
InvalidUserStatusException400status outside A/I/S
IncorrectPasswordException400wrong current password

11.2 Shared layer (common/exception & common/response)

  • GlobalExceptionHandler — a fallback advice that handles Bean Validation failures (MethodArgumentNotValidException → 400 with field messages), the shared exceptions, and any uncaught Exception (→ 500).
  • ErrorResponse — the uniform error body (status, message, path, timestamp).
  • ApiResponse<T> — a generic success wrapper available to all modules.

The module advice has highest precedence, so IAM-specific exceptions are handled with their precise statuses; anything it does not recognise falls through to the global handler.

14. Testing Strategy (JUnit 5 & Mockito)

The module ships with 127 automated tests across all three layers; the full suite passes (0 failures, 0 errors). Tests are the safety net that lets the team refactor confidently.

LayerTestsTechnique & what is validated
Service56Pure Mockito unit tests (@Mock repositories/encoder/JWT/audit, @InjectMocks service). Validate business rules, exception paths, and that the right collaborators are called. Mocking isolates the rule under test from the database.
Repository22@DataJpaTest against in-memory H2. Validate derived queries, the unique-email constraint, enum persistence, ordering, and associations.
Controller33Standalone MockMvc with mocked services and the real exception advice. Validate status codes, JSON shape, role enforcement (401/403), and validation (400).
Security16JwtService round-trip / tamper / expiry / issuer; AuthContext and AccessGuard behaviour.

Why mocking is required

A service test should fail only when the service logic is wrong — not because a database is down. Mockito supplies fake repositories whose responses we control, so each test exercises exactly one rule and runs in milliseconds. The repository tests, by contrast, use a real (in-memory) database because their whole purpose is to verify the queries.

Anatomy of a test

@ExtendWith(MockitoExtension.class)
class AuthServiceTest {
    @Mock UserRepository userRepository;       // controlled fake
    @InjectMocks AuthService authService;      // class under test
    @Test void login_wrongPassword() {
        when(userRepository.findByEmailIgnoreCase(...)).thenReturn(Optional.of(user));
        when(passwordEncoder.matches(...)).thenReturn(false);
        assertThatThrownBy(() -> authService.login(...))
            .isInstanceOf(InvalidCredentialsException.class);  // expected behaviour
    }
}

15. Logging & Observability

  • Audit logging is first-class: every state change writes an audit_log row via AuditService, queryable through admin endpoints for compliance.
  • SQL logging is enabled in development (spring.jpa.show-sql=true, formatted) to inspect generated queries.
  • Framework logging uses Spring Boot's default SLF4J/Logback. The seeder and filter emit context to the standard log.
